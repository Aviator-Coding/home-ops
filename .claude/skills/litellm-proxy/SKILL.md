# LiteLLM proxy, operator CRs and the auto-router

Relocated verbatim from `AGENTS.md` on 2026-09-01 so it loads only when this subsystem is in play.
The text below is unchanged; only line breaks were inserted. `AGENTS.md` keeps a one-sentence pointer.
Add new findings here or to the owning document, not back into `AGENTS.md` - see its
"Maintaining this file" section for the rule.

- **LiteLLM has no config-file-only way to declare a virtual key with a budget or rate limit** - keys with `max_budget`/`rpm_limit`/`tpm_limit` only exist via the proxy's `/key/generate` REST API, and without a connected Postgres `DATABASE_URL` that API stores keys in memory only (gone on every pod restart). This is why `ai/litellm` (governance layer, `docs/ai-system/litellm/README.md`) depends on the shared `postgres-17` CNPG cluster even though the rest of `ai/` is stateless-by-preference, and why its virtual keys are minted through that API rather than declared in `config.yaml`. Since captain decision O1 (2026-08-26) the minting is done by the **home-operations litellm-operator** (`kubernetes/apps/base/ai/litellm-operator/`, chart pinned in its `app/helmrelease.yaml`): `LiteLLMVirtualKey` CRs in `ai/litellm/app/virtualkeys/` replaced a hand-written `consumers.json` + `provision_keys.py` + hook Job + CronJob + RBAC, and `LiteLLMModel` CRs in `app/models/` replaced the `config.yaml` ConfigMap.

Eleven things to know before touching it:

(1) **`LiteLLMProxySpec` has no `securityContext`, `serviceAccountName`, `automountServiceAccountToken`, `strategy`, `initContainers` or `startupProbe` field**, so the operator-rendered proxy pod carries none of this repo's usual pod hardening and the `default` SA token *is* mounted - the accepted-gap table and why a kustomize patch cannot fix it (the operator reconciles that Deployment back) are in `kubernetes/apps/base/ai/litellm/README.md`.

(2) Because there are no initContainers, DB bootstrap is a standalone `postgres-init` Job (`app/dbinit.yaml`), **not** a CNPG `Database` CR: that CRD's `spec.owner` is required and CNPG does not create the role, which would force `spec.managed.roles` edits on the shared `postgres-17` Cluster.

(3) The operator's ValidatingWebhookConfiguration is `failurePolicy: Fail` for every LiteLLM kind, so `ai/litellm` must `dependsOn` `ai/litellm-operator` with a Deployment healthCheck - with the operator down the API server *rejects* the CRs rather than leaving them unreconciled.

(4) **LiteLLM key aliases are globally unique and the operator has no adopt-by-alias path**, so a key that already exists under an alias blocks forever the CR that wants it: `POST /key/generate` returns `400 Key with alias '<name>' already exists`. `LiteLLMVirtualKeyReconciler` only reaches its `GetVirtualKey`/`UpdateVirtualKey` branch when its own output Secret exists; with that Secret absent it can only ever retry `generate`. This bit the O1 cutover live on 2026-08-27 - the retired `provision_keys.py` keys survived in the Postgres DB the migration deliberately keeps, so both `LiteLLMVirtualKey`s sat `Ready=False`/`GenerateFailed` while the proxy looked perfectly healthy (Ready, 5 models rendered, still serving on the old keys) and the `PushSecret`s never wrote 1Password. Deleting the colliding key through the admin API (`POST /key/delete`) is therefore a **required** step, not tidy-up, whenever a key comes under operator management or an alias is reused. Expect the credential to rotate (the old value starts returning 401) and its accrued spend history to go with it, so treat it as a real rotation and check who holds that key first.

(5) **A config-declared fallback in `routerSettings` BYPASSES the calling virtual key's model allow-list.** Measured on v1.98.0: a key scoped to one local-shaped model was served by `anthropic/claude-sonnet-5` and billed real USD, having never named it - `litellm/router.py` and `router_utils/` contain no reference to the key's entitlements at all. A caller-SUPPLIED `fallbacks` array in the request body *is* checked (403), so only the router's own chain is unchecked. Consequence, and the reason `qwen3.6-35b-a3b` deliberately has NO fallback while the otherwise-identical `chat-ha` alias does: **a cloud fallback may only be declared on an alias whose every consumer is already cloud-entitled**, or captain decision D4's budget/entitlement split is silently void. Full evidence: `docs/ai-system/litellm/fallbacks.md`.

(6) **Never name a hand-written HTTPRoute after the `LiteLLMProxy` CR.** When `spec.route` is absent the operator DELETES any HTTPRoute whose name equals the proxy's name in that namespace, treating it as an orphan it owns - and it does so on the *next reconcile*, so the route works at first and vanishes days later. Ours is `httproute-internal.yaml`/`litellm-internal` for exactly this reason.

(7) **D4 rate limits and budgets need `litellm-dragonfly` (this repo's `kubernetes/components/dragonfly` on `kubernetes/apps/main/ai/litellm.yaml`) - `replicas: 1` is not enough.** LiteLLM runs multiple app workers inside one pod; without a shared Redis-API store, limits and spend are enforced per worker and can overshoot. Do not remove the component, the `routerSettings.redis_host`/`redis_port` wiring, or set `LITELLM_DISABLE_NO_REDIS_WARNING` to hide the banner - the fix is the store. Rationale and the verbatim banner text: `docs/ai-system/litellm/README.md#why-dragonfly-redis`.

(8) **Registering a `LiteLLMModel` grants nothing, and a model id is only valid on the route it came from.** `app/models/` grew from 6 to 32 CRs on 2026-08-27 (the captain's `indydevdan-model-stack` batch) with no allow-list, consumer-key or `auto`-router change, because a CR there only makes a model *callable by name* - entitlement is the separate D4 decision on a `LiteLLMVirtualKey`, and the sole way registration alone can spend money is a config-declared fallback (item 5). Route by the credential this repo actually holds - four fields of the one 1Password `ai-keys` item: `anthropic/`, `xai/`, `zai/` (a **native** provider on the pinned image, resolving to `https://api.z.ai/api/paas/v4` - no `apiBase` shim), and `openrouter/` for every other vendor. Never transcribe an id from a spreadsheet or a sibling provider's catalog: Anthropic's own API spells it `claude-opus-4-8` where OpenRouter spells the same model `anthropic/claude-opus-4.8`, and the dotted form is simply not a model on the direct route. Resolve every id against the catalog of the route you are taking, and note `apiKey: os.environ/<VAR>` is load-bearing at proxy **startup**, so deleting a key from `app/externalsecret.yaml` while any model still names it downs the proxy for every consumer. All four rules, with the verification commands: `kubernetes/apps/base/ai/litellm/README.md#model-catalog`.

(9) **A client-supplied `Authorization: Bearer sk-ant-oat...` header REPLACES the deployment's own `apiKey` on every Anthropic-family model, and no config flag gates it.** `add_provider_specific_headers_to_request` is called unconditionally (`litellm_pre_call_utils.py:1704` on v1.98.0), so this is true of the cluster as it stands - `forward_client_headers_to_llm_api` neither enables nor disables it, and that flag (which only forwards `x-*` + `anthropic-beta`, proxy-wide to *every* backend) is deliberately NOT set here; the narrow `litellm_settings.model_group_settings.forward_client_headers_to_llm_api` list form is the one to use if it is ever needed. Measured live 2026-08-27 (before the rename, against the model then named `claude-sonnet-5` - today `claude-sonnet-5-metered`): a fake token sent to it made Anthropic answer `"OAuth access token is invalid."`, proving our `ANTHROPIC_API_KEY` was never sent, and it also cooled that model group down for *all* consumers for ~60s. It is bounded (only that prefix, only anthropic/bedrock/vertex_ai, only when the caller authenticated via `x-litellm-api-key`) and it can **not** bypass a virtual key's allow-list - 403 is identical with and without the header - so D4 entitlement still holds. This is what `app/models/claude-sonnet-5.yaml` and `app/models/claude-opus-5.yaml` (renamed 2026-08-31 from `claude-code-subscription{,-opus}.yaml` - the two CRs for which the proxy holds **no** credential) deliberately exploit for Claude Code Max/Pro pass-through. Two traps it closes, both verified in-pod and both worth reusing: a model with **no** `apiKey` is not credential-less - `get_api_key` falls back to `os.environ/ANTHROPIC_API_KEY`, which the pod holds, so it would silently bill the metered account - and an explicit `$0` `info.extra` price IS honoured rather than read as unset (`use_custom_pricing_for_model` tests `is not None`), which is why the flat-rate CRs declare zero prices (no per-token invoice to match) - but **input/output zeros alone are not enough**: prompt-cache pricing has its own five fields (runbook §4a) and until those were zeroed on 2026-08-31 the key accrued ~$54 of cache-only fictional spend. With the full set declared, recorded spend is $0, so a `maxBudget` could never trip and would read as protection that does not exist; the dedicated key is budgetless and also carries no `rpmLimit`/`tpmLimit` (captain decision 2026-08-31), so enforcement is entirely upstream on Anthropic's subscription rate limiting, while `LiteLLMClaudeCodeSubscriptionSpendRegression` watches for phantom-spend regression (see `virtualkeys/claude-code-subscription.yaml` and `docs/ai-system/litellm/claude-code-subscription.md` §4b). Historical rows are not repriced. Mechanism, evidence tables and the client runbook: `docs/ai-system/litellm/claude-code-subscription.md`.

(10) **The Postgres spend log stores NO prompt or response content unless `generalSettings.store_prompts_in_spend_logs` is on** (default false; `_should_store_prompts_and_responses_in_spend_logs`, `proxy/spend_tracking/spend_tracking_utils.py:1162` on v1.98.0 - it is the only gate, reading that key or the `STORE_PROMPTS_IN_SPEND_LOGS` env var). It is on since 2026-08-27. Three non-obvious consequences. The prompt does **not** land in the `messages` column - that one stays `"{}"` for everything except the realtime API (`_get_messages_for_spend_logs_payload`, same file:637); read `proxy_server_request` (request body) and `response` instead, and note `request_id` is the *upstream provider's* response id (`gen-...`, `chatcmpl-...`), never the `x-litellm-call-id` the proxy returns. The flag alone does not give you the whole prompt either: every string over `MAX_STRING_LENGTH_PROMPT_IN_DB` (default 2048 chars) is head/tail stitched with a `litellm_truncated` marker, which is why `app/litellmproxy.yaml` also sets that env var. And **do not add `store_model_in_db: true`** even though the Admin UI's hint bundles the two - tested false-throughout and the `spend_tracking` package never references it; the UI bundles them only because its own Settings write path (`ProxyConfig.save_config`, `proxy/proxy_server.py:4188`) early-returns without it, and we declare the flag in `config.yaml` instead. Retention is set to `maximum_spend_logs_retention_period: "30d"` to match the shared `postgres-17` Barman `retentionPolicy: 30d` (captain decision `litellm-log-backup-export`, 2026-08-27, option C): that key is the built-in pruner's gate and nothing is scheduled while it is null (`proxy_server.py:8937`); enabling it deletes whole `LiteLLM_SpendLogs` rows so per-request cost history goes with the content, while durable `LiteLLM_Daily*Spend` rollups survive. Confidentiality: content leaves the k8s cluster only onto the LAN TrueNAS MinIO Barman target (no third-party/R2 path), caller credentials are redacted, LiteLLM cold-storage/callbacks stay closed. Retrieval runbook: `docs/ai-system/litellm/request-logs.md`.

(11) **A virtual key's `models` allow-list is checked against the RAW requested name, so per-key `aliases` cannot grant access to anything.** The CRD exposes `LiteLLMVirtualKey.spec.aliases` and it looks like the clean way to make one key's `claude-opus-5` mean something else, but on v1.98.0 the rewrite (`_update_model_if_key_alias_exists`, `proxy/litellm_pre_call_utils.py`) runs inside `add_litellm_data_to_request` - i.e. *after* `can_key_call_model` (`proxy/auth/auth_checks.py`) has already returned 403 from the `user_api_key_auth` dependency, and that check consults `team_model_aliases` only (there is no `_model_in_key_aliases`). Measured 2026-08-30 with a throwaway aliased key: identical 403. Making an alias fire therefore requires ALSO allow-listing the target's original name, which on a metered model is the money leak the allow-list exists to prevent - so **never reach for aliases to solve a name collision**; add a distinct model name (or, if nothing already holds the natural name, own it outright) and resolve any remaining collision client-side. This is exactly what forced the Claude Code Max/Pro pass-through into `ANTHROPIC_DEFAULT_OPUS_MODEL`/`_SONNET_MODEL` overrides from 2026-08-30 to 2026-08-31, when `claude-opus-5`/`claude-sonnet-5` (the natural names Claude Code requests by default) still meant the METERED CRs: `ANTHROPIC_MODEL` only names the main loop's model, so a by-family request (a subagent, `/model opus`) resolved through those vars and, left unset, asked this proxy for the metered route. **That collision no longer exists**: the 2026-08-31 rename (captain decision, Alternative B of the pass-through investigation) moved the metered CRs to `claude-sonnet-5-metered`/`claude-opus-5-metered` and let the pass-through CRs own the natural names outright, so the client-side overrides were removed - do not re-add them or assume they are still required. An admin who deliberately wants the metered route now asks for the `-metered` name and is documented, not silently rebound. Both pass-through CRs and the full client contract: `docs/ai-system/litellm/claude-code-subscription.md` §5c/§7/§8. That doc's §4a also carries a trap worth knowing before zero-rating ANY model: **`input_cost_per_token`/`output_cost_per_token: 0` is not enough** - prompt-cache pricing lives in its own five `_CACHE_PRICING_FIELDS`, which `_resolve_builtin_model_cost_entry` copies from the built-in cost map onto the custom key, so they keep billing. Claude Code caches almost every turn, so that gap put ~$54 of fictional spend on the subscription key (measured: `output_cost` exactly $0.00, `cache_read` + `cache_creation` the entire total) until all five were zeroed on 2026-08-31. Route is irrelevant - it reproduces identically on `/v1/chat/completions` and `/v1/messages`. Historical rows are not repriced, so a non-zero total on that key is history, not live spend.

- **A reasoning model cannot be used as a LiteLLM auto-router classifier without explicitly disabling thinking, and the failure is silent.** The `ai/litellm` complexity-tier auto-router (`auto` alias, captain decision D3) classifies each request with the LOCAL `qwen3.6-35b-a3b`, which is a *thinking* model: by default llama.cpp returns its ~1300 reasoning tokens in `reasoning_content` and leaves `content` **empty**, so LiteLLM's structured-output parse raises "empty content" and **every** classification fails. The router then fails open on 100% of traffic - it looks perfectly healthy, serves every request, and simply never routes anything to a cloud tier. The fix is the dedicated `qwen3.6-35b-a3b-classifier` deployment carrying `extra_body.chat_template_kwargs.enable_thinking: false` (measured 2026-08-26: 12/12 unparseable without it, 11/12 correct with it); `reasoning_effort: none`, `chat_template_kwargs.thinking` and `chat_template_kwargs.reasoning_effort` were all tested and do **not** work on this llama.cpp build. That deployment also carries `num_retries: 0`, because the classifier's timeout rides in front of every routed request. Two more traps in the same feature: `classifier_type: llm` only exists from **LiteLLM v1.93.0** and `ComplexityRouterConfig` is `extra="allow"`, so on an older image the whole LLM-classifier config parses clean and is silently ignored in favour of the 25%-accurate rule-based scorer; and the tier rubric defaults to the uncalibrated `legacy` preset, which grades ordinary engineering as top-tier and sends routine agent traffic to the most expensive model (`classification_rubric: agentic` is the calibrated one). Fail-open-to-local is pinned by `litellm_params.complexity_router_default_model` (the field `init_complexity_router_deployment` actually reads) kept aligned with in-config `default_model` - without that sibling, fail-open falls back to the MEDIUM then SIMPLE tier, so retargeting MEDIUM to cloud while leaving `classifier_fallback: default_model` would silently burn cloud spend on classifier failures. Measured latency, accuracy, budget behaviour, the Prometheus label scheme the alerts are built on, and the tuning table: `docs/ai-system/litellm/auto-router.md`.
