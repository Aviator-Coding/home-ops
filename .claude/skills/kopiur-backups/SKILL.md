# kopiur backups (and the VolSync dual-engine overlap)

Relocated verbatim from `AGENTS.md` on 2026-09-01 so it loads only when this subsystem is in play.
The text below is unchanged; only line breaks were inserted. `AGENTS.md` keeps a one-sentence pointer.

- **kopiur is live on all 30 of the fleet's 30 VolSync-protected claims, VolSync has been RETIRED from four of them (migration Stage 5 pilot, 2026-09-01), and deleting kopiur's CRs can delete backup data.** `system/kopiur` (operator + two cluster-scoped `ClusterRepository` objects: `ceph` and `r2`, each on its own new `kopiur` bucket - MinIO is deliberately not a kopiur destination) is the staged replacement for VolSync. Stage 3 (2026-08-30) put 27 further claims on `kubernetes/components/kopiur` **alongside** an untouched `components/volsync`, one commit per namespace, so those claims now have two independent backups each.

**Four volumes are now kopiur-ONLY** - `ai/repo-wiki`, `downloads/recyclarr-config`, `downloads/sabnzbd-config`, `media/seerr`, retired 2026-09-01 as a deliberate low-stakes pilot (regenerable or reconstructible content, clean restore proofs); the other 26 still run both engines and retiring any of them is a separate captain decision. Stage 4 (2026-08-31) onboarded both previously deferred claims: `selfhosted/changedetection-config`, which turned out **not** to need the `0:1000` root mover its deferral assumed (the app shipped **no `securityContext` at all**, so it ran as its image default (root) and wrote 2292 mode-`0600` root-owned files while its overlay declared an `APP_UID`/`APP_GID` of 2000:2000 that **no manifest in this repo consumes**; giving it the 1000:1000 identity its data already carried and re-owning the volume removed the need for a root mover, so it onboarded with no `KOPIUR_PUID`/`PGID` override and no namespace-wide privileged-mover grant), and `home-automation/matter-server` with an explicit root mover (`KOPIUR_PUID/PGID: 0`) - the component already parameterises that, so inheritSecurityContextFrom was not used (it would not flow to the standing Restore) - plus the namespace-wide `kopiur.home-operations.com/privileged-movers=true` annotation.

**All 30 claims are restore-proven on BOTH destinations** (2026-09-01, `docs/backups/kopiur-restore-proof-2026-09-01.md`) - that fleet proof is the Stage 5 prerequisite and is what authorised the four retirements above; it records the state *before* them, and its finding 2 (an r2 restore needs materially more kopia cache than the same restore from ceph - `media/plex` succeeded from ceph at 2Gi and FAILED from r2 at the same size, and a failed `Restore` is terminal) **was closed for `ai/hermes` on 2026-09-02** by raising it to 16Gi and re-proving an r2 restore at that exact value (`docs/backups/kopiur-r2-restore-cache-gate-2026-09-02.md`, now the authority on cache sizing); `media/plex`'s standing 10Gi is predicted safe by that run's measurement but has not itself been exercised against r2.

**Retiring a volume is a PVC-ownership swap, and getting it wrong deletes the volume**: `components/volsync/pvc.yaml` is the only manifest emitting an app's claim and every overlay runs `prune: true`, so a retired app must add `kubernetes/components/kopiur/pvc` - which exists as a separate Component precisely because folding it into `components/kopiur` would collide with volsync's PVC for every app still dual-engine. That file must carry `kustomize.toolkit.fluxcd.io/ssa: IfNotPresent` and must NEVER carry `force: enabled`: `dataSourceRef` is **immutable on a bound PVC** (measured - a server-side dry-run of the swap returns `spec: Forbidden: spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims`, and omitting the field is the same forbidden change because SSA would remove it), so `IfNotPresent` keeps the claim inventoried while skipping the apply, and `force` would resolve the conflict by deleting and recreating the data volume. A live claim therefore keeps an inert `dataSourceRef` pointing at a deleted `ReplicationDestination`, which is correct - it is consulted once at provisioning. Retirement mechanics, per-volume rationale and the post-retirement re-proof: `docs/backups/kopiur-stage5-pilot-retirement-2026-09-01.md`; the machine-readable single-engine record is `RETIRED_CLAIMS` in `scripts/ci/kopiur-stage3-test.py`, asserted both ways. Authoritative onboarded claim list: `kubernetes/components/kopiur/Readme.md`. Restore-proof authority: `docs/backups/kopiur-restore-proof-2026-09-01.md`.

Stage 2's restore gate **passed** on 2026-08-30 - `sabnzbd-config` restored byte-identically (2062 files, 2.06 GiB, per-file sha256, modes and ownership included) from **both** destinations; the durable drill procedure is `docs/backups/kopiur-restore-drill-2026-08-30.md`. That document also records two findings - at Stage 1 time `autobrr` held **zero** files (app state is in `postgres-17`; a later write-access fix let it create `config.toml`, but the lesson stands), so Stage 1's "Snapshot `Succeeded`" gate was met by a volume that moved no data, and a `Succeeded` snapshot is therefore not evidence of anything until you have checked `.status.stats` is non-zero. The load-bearing difference from VolSync: a kopiur `Snapshot` CR **owns** its kopia snapshot through a finalizer, so deleting CRs deletes backup data, whereas deleting a `ReplicationSource` never touches the restic repository. Upstream ADR-0006 records a real incident where ownerReference GC fired 600-700 concurrent snapshot deletions at one repository, and **we run Flux with `prune: true`, which is that exact shape** - hence `deletionProtection.threshold`/`onNamespaceDelete` pinned on the repositories and `deletion.onPolicyDelete`/`onScheduleDelete: Retain` pinned on every policy and schedule in the component.

Ten traps (Stages 1-4 plus the 2026-08-31 timezone and alert-cadence fixes), none of which any manifest test catches.

(0) **The mover's identity must match the workload that owns the claim's files, or the backup FAILS - `KOPIUR_PUID`/`KOPIUR_PGID` default to 1000 and are not cosmetic.** Any file with no world-read bit is unopenable by a non-matching uid, and kopia treats that as fatal: `sabnzbd-config` (app uid 2000, seven 0600/0660 files) failed on **both** destinations until the pair was set to 2000. kopiur fails closed rather than writing a partial snapshot, and its admission webhook warns at apply time - never dismiss that warning. VolSync survives the identical mismatch (same `VOLSYNC_PUID:-1000` default) only because it mounts its staged clone **writable**, so kubelet's `fsGroup` walk rewrites group ownership and permissions before restic reads it; kopiur mounts the staged source `readOnly` (`sources[].readOnly` defaults true) and kubelet applies no `fsGroup` to a read-only mount. That difference is also why a kopiur restore reproduces the **original** modes. Measure the claim's **file** ownership before onboarding - do not infer the mover identity from the pod's `runAsUser` (see trap 6).

(1) **A `ClusterRepository` mover Job runs in the WORKLOAD namespace and loads credentials with `envFrom`, which is namespace-local**, so a repository whose Secrets are pinned to `system` backs up nothing outside `system` - the CRs reconcile perfectly clean and the mover fails at run time. The answer we run is `credentialProjection` (captain decision 2026-08-30, key `credential-scope`), which mints the credential into the mover's namespace for the run and reaps it, so **no repository credential sits at rest in any app namespace** - the pilot's `downloads`-only ExternalSecret copies and its restricted `ClusterSecretStore` were deleted with it, and must not be reintroduced. It is gated in **three** places and all three are required; miss leg 2 or 3 and every CR still goes green while the mover fails at run time (leg 1 at least surfaces a 403 in status): (a) `features.credentialProjection.enabled` on the HelmRelease - the operator RBAC, (b) `credentialProjection.allowed` on **both** `ClusterRepository` objects - the owner gate, (c) `credentialProjection.enabled` on each consuming `SnapshotPolicy`/`Restore` - the consumer opt-in, which lives in `kubernetes/components/kopiur/` so any app onboarded through the component gets it for free. Also load-bearing: every `secretRef` in the repository spec must set `namespace:` **explicitly**, or the operator does not know what to copy. **Accepted cost, not glossed:** leg (a) is the only thing adding `create`/`patch`/`delete` on `secrets` to the operator's ClusterRole and `create` cannot be scoped to a name, so a compromised kopiur operator is a cluster-wide credential-rewrite primitive - do not widen it further (notably `features.kopiaUi` wants the same verbs and is NOT covered). Watch the right signal: `kopiur_projected_secrets_live` is a POPULATION gauge sampled on a periodic sweep, not a per-run indicator - measured 2026-08-31, two projected Secrets lived ~90s during a real backup and the gauge read 0 at every 30s scrape, so a flat 0 during a run is correct and is NOT evidence projection is off. Alert on the value staying above zero across multiple sweep passes, not one frozen reading (our `KopiurProjectedCredentialsLeaking` uses `min_over_time(kopiur_projected_secrets_live[13h]) > 0`; none of the chart's 12 alerts cover it) - see trap (9) for why a bare `> 0` for a fixed duration false-fired for hours on a fleet with no leak at all, and upstream's deriv prescription separately misses a one-shot permanent leak that steps 0 to N and stays flat. Per-run evidence is the operator log `reaped projected credentials copy secret=<snapshot>-creds-N` plus `kopiur_secrets_projected_total` - NOT `Snapshot.status.cleanup.credsReapedAt`, which is set on every run whether projection is on or off. One trap: `components/kopiur/ceph/restore.yaml` carries `ssa: IfNotPresent`, so leg (c) never reaches a `Restore` that already exists - hand-written drill Restores need `credentialProjection: {enabled: true}` in their own spec. Full rationale: `kubernetes/components/kopiur/Readme.md` "Credentials".

(2) kopiur accepts **bare `H` only** in a cron - Jenkins range syntax `H(0-19)` is webhook-rejected - so a hashed minute cannot be bounded away from VolSync's; the component separates the two systems by the **hour** field instead.

(3) `Restore.spec.source.fromPolicy` has no `pvc` field, which is why `sources[].pvcSelector` is not used despite removing the one-Kustomization-per-claim tax. kopiur's Ceph bucket is an `ObjectBucketClaim` on `ceph-bucket`, matching `volsync/backend/` - that StorageClass is `reclaimPolicy: Delete`, but so is the live `volsync` OBC that has held our Ceph backups for 328 days, so it is a property of the established pattern and not a reason to hand-make a one-off (captain decision 2026-08-30); addressing it at all must cover the volsync bucket too. Credentials follow the `litellm-consumer-*` one-item-per-purpose convention (`kopiur-ceph`, `kopiur-r2`, `kopiur-ceph-bucket` in Homelab; the last is a record nothing reads - the operator projects the Ceph S3 keys from the OBC's own generated Secret instead), and nothing kopiur owns reads the live `volsync-template` item. Stage 0 scope, prerequisites, rollback and upgrade discipline: `kubernetes/apps/base/system/kopiur/README.md`.

(4) **The component ships a standing `Restore` in passive populator mode that reports `Ready=False` for the whole parallel run BY DESIGN** (`AwaitingPvcDataSourceRef`). Bound claims never repoint: `spec.dataSourceRef` is immutable, so a live claim keeps its (now often inert) VolSync ref forever and the standing Restore stays Pending until a **rebuilt** claim from `components/kopiur/pvc` claims it - already the contract on the four Stage 5 pilot volumes. So the component **cannot be added inline to a Flux Kustomization with `wait: true`**, which makes Flux assess every object in the inventory and therefore block on an object that can never become Ready. Two apps hit this and ship the kopiur half as their own `wait: false` Kustomization pointed at `./kubernetes/components/kopiur/backup`: `database/pgadmin` (in `kubernetes/apps/main/database/cloudnative-pg.yaml`) and `media/calibre-web-automated`. An overlay with `wait: false` plus explicit workload `healthChecks` is unaffected, because Flux then assesses only the listed objects. `flate` does not catch this - it validates the build, not Flux's runtime health assessment.

(5) **`KOPIUR_SCHEDULE_R2` must be set per namespace; the component default `H 4 * * *` is wrong at fleet scale.** It would put every kopiur r2 policy into the single 04:00 hour, which already carries VolSync's whole ceph slot plus 13 VolSync r2 runs - 83 mover runs, making it the busiest hour of the day, and for every `selfhosted` claim and `media/calibre-web-automated` it would stack both engines into the same hour for the same claim. The live assignment is one free hour per namespace: `database` 07, `home-automation` 10, `downloads` 11, `selfhosted` 14, `media` 15, `ai` 19. **`KOPIUR_SCHEDULE_CEPH` stays at the component default** - it is already structurally offset onto the odd 4-hour slots (01/05/09/13/17/21) against VolSync's even ones. Never hand-assign minutes; `H` is hashed and `jitter: 5m` decorrelates on top.

(6) **Do not infer a mover identity from the pod's `runAsUser` - measure the FILES.** Stage 3 measured all 30 mountable claims live; `media/plex`, `media/tdarr-config` and `media/calibre-web-automated` all run `runAsUser: 0` with `fsGroup: 2000` while owning their files `2000:2000`, and `ai/hermes` pins **no** `runAsUser` at all (only `fsGroup: 10000`) while owning 104,060 entries `10000:10000` - 1,948 files and 310 directories of which are unreadable at the default, so it would have failed closed on the largest volume in the fleet. 10 of the 33 volumes surveyed needed a non-default identity. The authoritative measured table is `EXPECTED_IDENTITY` in `scripts/ci/kopiur-stage3-test.py`; each onboarded overlay also records the pair inline. `downloads/recyclarr-config` is the one identity taken from a declared pod `securityContext` rather than live measurement, because it is a CronJob whose pod exists ~18 s/day - its manifest says so.

(7) **kopiur ignores the cluster-wide `k8tz`-injected `TZ` and defaults its cron to UTC; VolSync honours it.** Both engines get `TZ=America/New_York` from the `k8tz` webhook, but only VolSync's Go scheduler uses it - kopiur resolves UTC regardless, unless `spec.schedule.timezone` (IANA) is set on the `SnapshotSchedule`. The deliberate 1-hour ceph/r2 stagger between the engines survived only by coincidence (offset 4 mod period 4 == 0 in EDT) and would have collided on all 29 dual-engine claims at the 2026-11-01 DST transition. Fixed 2026-08-31 by setting `spec.schedule.timezone` (via `KOPIUR_SCHEDULE_TIMEZONE`, default `America/New_York`, matching VolSync) on both the ceph and r2 `SnapshotSchedule`s. Full measurement and the resulting hour tables for both DST seasons: `kubernetes/components/kopiur/Readme.md` "Timezone: kopiur vs VolSync".

(8) **A root mover (`runAsUser: 0`) is admitted on the SnapshotPolicy and refused on the Snapshot.** Measured 2026-08-31: the validating webhook lets the policy through, then the Snapshot sits `Pending` with `MoverPermitted=False` / `PrivilegedMoverNotPermitted` until the namespace carries `kopiur.home-operations.com/privileged-movers=true`. Apply that annotation through GitOps on the overlay that actually produces the Namespace (`kubernetes/apps/main/home-automation/kustomization.yaml` patches `not-used`, the common component's pre-transform name) - `kubernetes/apps/base/home-automation/namespace.yaml` is not in any Flux inventory, and `kustomize.toolkit.fluxcd.io/prune: disabled` only prevents DELETE, it does not freeze annotations. The annotation is namespace-wide (all four `home-automation` claims), but it is a gate, not an identity change: the other three keep their non-root movers. A root restore mover preserves modes and file content but materialises mixed live uids as `0:0` (matter-server: 151 files were `1000:0` live and `0:0` restored; the five `0600` fabric files stayed `0:0`). The app runs as root, so that is functional, and it is not a content-fidelity failure. Component, schedules, restore-vs-drill and rollback: `kubernetes/components/kopiur/Readme.md`.

(9) **`kopiur_projected_secrets_live` is a leader-only periodic census (set once per `KOPIUR_WORK_SPEC_SWEEP_INTERVAL_SECS`, default 6h, from `run_sweep`/`spawn_sweep` in `ghcr.io/home-operations/kopiur-controller`), not a live/continuous gauge - a fixed-duration `for:` on a bare `> 0` false-fires for hours whenever one sweep pass happens to catch a wholly benign moment (several concurrent mover runs each briefly holding a credential Secret) and freezes that reading until the next pass, which is longer than any reasonable `for:` window.** Confirmed live 2026-08-31: only the Lease-holding replica exports this series at all (the standby exports none of it, so there is no per-replica double-counting to guard against), and Prometheus's stored series showed the gauge step 0->4->0 across exactly two 6h-apart sweep passes while zero Secrets existed in the cluster on both sides of the plateau. Fixed by requiring the value to stay positive across at least two sweep passes (`min_over_time(...[13h]) > 0`) rather than one frozen reading for an hour - full mechanism, evidence, and the true-positive reasoning for why a genuine one-shot leak is still caught (it never returns to zero on any subsequent sweep) are in `kubernetes/apps/base/system/kopiur/app/prometheusrule.yaml` next to the `KopiurProjectedCredentialsLeaking` rule; the behavioral pin is `scripts/ci/kopiur-projected-secrets-leak-alert-test.py`.

- **All 30 kopiur claims are restore-proven on both destinations, and the proof run surfaced three things that change how you read a kopiur backup.** Full per-volume evidence table (snapshot state, live vs snapshot vs restored file counts, per-tree sha256 digests, pass/fail against all four criteria): `docs/backups/kopiur-restore-proof-2026-09-01.md`; the procedure it follows is `docs/backups/kopiur-restore-drill-2026-08-30.md`.

(a) **kopia honours `CACHEDIR.TAG` and silently omits those directories' contents, so a correct restore legitimately holds FEWER files than live.** The directory itself comes back with mode and ownership intact; only its contents are skipped. Three claims are affected fleet-wide - `ai/hermes` (23,467 files: `uv` caches, four venvs, a pytest cache), `home-automation/home-assistant` (17, `.venv`), `media/calibre-web-automated` (14, `.cache/fontconfig`) - and `snapshot filesNew` equals the restored count exactly in each, which is the signal that the omission is deliberate rather than lossy. **VolSync's restic mover sets no `--exclude-caches` and nothing in `kubernetes/components/volsync/` configures it**, so the restic repositories very likely still hold this content. That gap was **adjudicated on 2026-09-01 and is NOT a blocker**: all 23,467 `hermes` files are under a validly-signed tag, every root is a stock venv or a `uv`/`pytest` cache, no user-authored file exists inside any of them, and the largest venv (`wiki/.venv`) rebuilds from `wiki/{pyproject.toml,uv.lock}` which ARE in the backup - so kopiur is a faithful, not lossy, replacement on that volume. **This is not a Stage 5 blocker.** The remaining DR prerequisite was (b) below, now closed for `ai/hermes`.

(b) **Sizing `KOPIUR_CACHE_CAPACITY` is a RESTORE question, and getting it wrong fails terminally - measured 2026-09-02.** During a restore the kopia cache grows **~1:1 with the bytes written into the restore target** until it reaches kopia's own internal budget - observed as a **~6.2 GiB plateau** - and only then holds flat. So **required cache = min(snapshot `sizeBytes`, ~6.2 GiB)**, plus headroom, and **it is a cliff, not a slope**: while a claim's snapshot is smaller than its cache the limit is never reached and any value works, but the first time a growing claim crosses its capacity the requirement jumps straight to the full plateau. That is why `ai/hermes` (9.70 GiB snapshot) could never restore on its old 5Gi - it ran out at ~45% restored - while most claims still sit safely under the 2Gi default. **Do not lean on the plateau**: kopiur sends `"cache":{}` in its work spec and neither `ClusterRepository` sets `cacheDefaults`, so kopia's built-in (unpinned) defaults govern eviction; the CRD does expose `mover.cache.contentCacheSizeMb`/`metadataCacheSizeMb`, which nothing in this repo sets and which is the structural fix if these capacities ever get expensive. Cost is not a reason to under-size: `mode: Ephemeral` renders a generic ephemeral **PVC** on `ceph-block` (NOT an emptyDir - a comment in `hermes.yaml` claimed otherwise until 2026-09-02), thin-provisioned and deleted with the mover pod. One variable feeds both backup policies and the standing `Restore`; the restore sets the value. `ai/hermes` is now 16Gi and **proven from r2 at that value**; `media/tdarr` and `downloads/radarr` were raised 2Gi -> 10Gi on 2026-09-02 (they were at 87% and 70% of usable), with `media/tdarr` **r2-proven at 10Gi** - 17,281 files / 1,820,653,922 bytes restored, matching its snapshot's `filesNew`/`sizeBytes` exactly, 0 mode or ownership differences across 24,054 entries. A failed `Restore` is terminal and never retries, so recovery means creating a NEW `Restore`, never patching the old one. Cache curve and sizing model: `docs/backups/kopiur-r2-restore-cache-gate-2026-09-02.md`; tdarr/radarr raise and tdarr r2 proof: `docs/backups/kopiur-populator-drift-2026-09-02.md`.

**(b-bis) The standing populator does NOT pick up a raised `KOPIUR_CACHE_CAPACITY`, or any other changed `KOPIUR_*` value, and the divergence is permanent and silent** - `components/kopiur/ceph/restore.yaml` carries `kustomize.toolkit.fluxcd.io/ssa: IfNotPresent`, so Flux applies it once at creation and never reconciles it again, while the owning Kustomization keeps reporting `Ready: True` / `Applied revision: main`. `flate` cannot see it either, because it validates the built manifest rather than the cluster. Found live on `ai/hermes` (Git 16Gi, live **5Gi** - the value already proven unable to restore that claim) and, in the fleet audit that followed, on `downloads/autobrr`, the Stage 1 pilot object, which had **two** fields frozen at their 2026-08-30 create-time values: identity `1000:1000` where Git says `2000:2000`, and **no `credentialProjection` at all** - either of which fails its restore closed. **A full 30-populator audit on 2026-09-02 found exactly those two and no others; all 30 now agree with `main`.** (The same day's tdarr/radarr 2Gi->10Gi raises needed their own post-merge delete+reconcile, since GitOps cannot recreate them at 10Gi while `main` still says 2Gi; **that was carried out and verified live on 2026-09-02 once #1544 had merged** - both now read `10Gi`, recreated `16:38:04Z`/`16:38:06Z`, so populator drift is 0 of 30 against `main`. `docs/backups/kopiur-wave-two-reproof-2026-09-02.md`.) The remedy is always delete + `flux reconcile`, never a patch, and it must run **after** the raising commit is on `main` or Flux just recreates the old value. Deleting a `Restore` is safe and was established four ways (no data-lifecycle field in the CRD, read-only data flow, 0/30 carry finalizers vs 276/276 `Snapshot`s, and an *active* restore observed carrying none mid-run); the `Snapshot` census was 276 before and after. Audit table, proof and the post-merge command: `docs/backups/kopiur-populator-drift-2026-09-02.md`. Two drill traps from these runs: a hand-written `Restore` needs `credentialProjection: {enabled: true}` in its OWN spec (the component's `ssa: IfNotPresent` never reaches an existing object); and when diffing restore manifests export `LC_ALL=C` for `sort` **and** `comm` together - a C-sorted file compared by a UTF-8-locale `comm` yields silent false "missing" paths (a phantom 10-file gap in the 2026-09-01 run), which keying comparisons on raw path bytes avoids structurally.

(c) **Reading a claim's "live" content through its own app pod can include bytes the claim does not hold.** `home-automation/esphome-config` scored a false FAIL because `/config/secrets.yaml` is an ESO Secret volume mounted OVER the claim path; the claim holds a zero-byte placeholder, which is what kopiur correctly backed up and restored. `find -xdev` does not save you: it declines to *descend* into another filesystem but still reports a single bind-mounted file inside a same-device directory. Compare the device (`stat -c %d`) or, better, read the live reference from a CSI `VolumeSnapshot` clone. Exactly four mounts land inside a backed-up data dir fleet-wide and this is the only file-level one; the other three are `emptyDir` directories, which `-xdev` prunes correctly. Also worth knowing: a restore-target PVC does **not** inherit its `Restore`'s labels, so a label-only cleanup sweep misses it.

(d) **The L1/L2 "stable set" bracket cannot see page-cache lag, so a file can sit in the stable set and still legitimately differ in the restore - treat such a mismatch as a question, not automatically as a failure.** `copyMethod: Snapshot` backs up a CSI block-level `VolumeSnapshot`, which is **crash-consistent, not filesystem-flushed**: bytes the app has written but that are still dirty in the page cache (or mmap'd and never written back) are simply not in the block image, and *both* halves of the bracket read through the filesystem and therefore see the same cached view the snapshot does not have. Measured on `ai/hermes` 2026-09-02: 2 of 65,968 compared files mismatched, and both were benign - `cron/usage_audit.jsonl` restored byte-identical to the **first 610,304 bytes** of the live file (a strict prefix of an append-only log), and `kanban.db-shm` came back as SQLite's 3-byte placeholder with a 0-byte `-wal` and a byte-identical `kanban.db`, i.e. nothing unreplayed. Check for a prefix relationship or an app-managed ephemeral file before concluding fidelity loss. This is inherent to snapshot-based backup and applies identically to VolSync. Two further cosmetic non-defects from the same run: a restored volume's **root directory** is provisioned by CSI and never restored by kopia (`hermes` live `0700 10000:10000` vs restored `2775 0:10000`), and a non-root mover cannot reproduce a root-owned entry (one `uid 0` directory came back as the mover's uid). Everything else was exact - **0 mode and 0 type differences across 77,776 entries**, which is the read-only-staging property that makes a kopiur restore mode-faithful where a VolSync restore relaxes every mode by a group-write bit.

(e) **Creating a `Snapshot` CR is not a read-only act - it can delete an existing backup, because a new snapshot pushes an older one past GFS retention and scheduled snapshots carry `deletionPolicy: Delete` plus the `snapshot-cleanup` finalizer.** Measured 2026-09-02: two hand-made `prowlarr` verification snapshots caused kopiur to prune exactly two older ones, with the operator naming both (`pruned backup (GFS retention) config=prowlarr-ceph backup=prowlarr-ceph-20260901172248`, then `snapshot deleted by batch Job; finalizer removed snapshot_id=2dc7face…`). **The `r2` case is the sharp one and applies to every `r2` policy in the fleet:** `r2` retention is `keepDaily/keepWeekly/keepMonthly` with **no `keepHourly` tier**, so only the *latest* snapshot of each day survives - meaning any on-demand `r2` snapshot **evicts that day's previously-newest one**, and a drill taking several would walk the daily tier backwards. (`ceph` has `keepHourly: 6`, so it absorbs one extra snapshot by retiring an hourly slot a little early.) **So prefer restoring from an existing scheduled snapshot**: for a static volume the existing `ceph` and `r2` snapshots already hold identical content and no new CR is needed at all - five claims were re-proven destination-identically on 2026-09-02 with zero `Snapshot` CRs created. Create a verification snapshot only when destination-identity genuinely needs a matched pair, and expect it to cost the oldest snapshot in the tier it lands in. Corollary for reporting: a "`Snapshot` census unchanged" check is not a meaningful safety invariant on this cluster (schedules and retention both move it continuously); the invariant that carries the meaning is *every snapshot that disappeared is attributed*.
