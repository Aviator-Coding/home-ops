# PROJECT KNOWLEDGE BASE

Home-ops GitOps repo for a 3-node Talos Linux Kubernetes cluster managed by Flux v2. `CLAUDE.md` is a symlink to this file. For narrower operator detail see [`talos/AGENTS.md`](talos/AGENTS.md) and [`bootstrap/AGENTS.md`](bootstrap/AGENTS.md).

**Core stack**: Talos Linux (immutable OS) + Flux v2 (GitOps) + Cilium (CNI, BGP LoadBalancer, kube-proxy replacement, no L2 announcements) + Rook-Ceph (storage) + External Secrets Operator/1Password (secrets) + Cloudflare Tunnel (external access) + External-DNS (split DNS: `network/cloudflare-dns` public, `network/unifi-dns` internal) + VolSync (triple-destination backup). Gateway API `HTTPRoute`s front `envoy-internal`/`envoy-external` gateways in `network`. Monitoring: kube-prometheus-stack + Loki + Promtail + Tempo + Grafana + Alertmanager + Gatus + kromgo + KEDA + unpoller, all in `monitoring`.

## CONVENTIONS

- **YAML schemas**: Every manifest starts with `# yaml-language-server: $schema=...` comment
- **Kustomization anchors**: `name: &app myapp`, `namespace: &namespace myns` - referenced via `*app`, `*namespace` on overlay `kubernetes/apps/main/<ns>/<app>.yaml`
- **Schema URL**: Prefer `kubernetes-schemas.pages.dev` - never `crd.movishell.pl` or `fluxcd-community`. When that host does not serve the kind as JSON, use the existing fallback `k8s-schemas.home-operations.com` (do not invent a third host or point at a URL that 404s).
- **Naming**: All lowercase, kebab-case dirs/files. `helmrelease.yaml`, `kustomization.yaml`, overlay `<app>.yaml`, `externalsecret.yaml`
- **Commit format**: `type(scope): description` - types: feat, fix, chore, ci, docs, refactor, test. Authoritative rules: `.commitlintrc.yaml` (commit-msg hook in `.pre-commit-config.yaml`)
- **Commit scopes**: container, helm, github-action, mise, talos, flux, deps, github-release, or app/namespace names
- **Gateway API**: `envoy-internal` (private) and `envoy-external` (public) in `network` namespace
- **DNS annotation**: `external-dns.alpha.kubernetes.io/target: "internal.${SECRET_DOMAIN}"` or `"external.${SECRET_DOMAIN}"`
- **Homepage annotations**: `gethomepage.dev/*` annotations on HTTPRoutes for dashboard integration
- **Gatus monitoring**: `gatus.home-operations.com/endpoint` annotation with conditions on HTTPRoutes
- **HelmRelease defaults**: Auto-patched by cluster-apps Kustomization - CRD CreateReplace, rollback recreate, upgrade remediation

## ANTI-PATTERNS (THIS PROJECT)

- **NEVER** put plaintext secrets in Git. App secrets are ExternalSecret + 1Password only. Bootstrap/Talos secrets are `ref+op://Home-Lab/...` resolved by `vals`.
- **NEVER** add a helm `postRenderer: bash` (breaks on Helm 4)
- **NEVER** run `just bootstrap cluster` / `apps` against a healthy cluster. See `bootstrap/AGENTS.md`
- **NEVER** commit without pre-commit file/security hooks - `task setup-dev-env` to install them
- **DO NOT** store secrets in `**/resources/**` - Renovate ignores this path
- There is no SOPS/age path and no `talos/clusterconfig/` or `talos/talconfig.yaml`. Do not reintroduce them.
- **NEVER rename a DRM device node with `generic-device-plugin`'s `mountPath`, and never ship a GPU change without running the VA-API check.** The `b70` group's remap to `card0`/`renderD128` is fatal to VA-API (libdrm reopens the canonical `DEVNAME` from sysfs, which the container does not have), while Level Zero is unaffected - so **the AI stack stays green while transcoding is completely dead**, an asymmetry that hid a total 3-day Tdarr outage. VA-API consumers must use `devic.es/b70-vaapi`, and allocatable capacity is not proof that transcoding works. Mechanism, the two related device-ID and `subPath` traps, and the verification commands: skill `intel-gpu`, `docs/media-stack.md` "Verifying VA-API after a GPU change", `docs/ai-gpu-changelog.md` (2026-08-29).
- **kagent / kmcp are not deployed** (removed 2026-06-07, #941/#942). Live AI stack is Hermes + ToolHive + agentgateway. `docs/ai-system/{kagent,kmcp}` are tombstones. ToolHive `MCPServer` is `toolhive.stacklok.dev/v1alpha1` - never kagent.dev's same kind name.
- **NEVER add a `CiliumClusterwideNetworkPolicy` that carries a `nodeSelector` and an `ingress:` (or `ingressDeny:`) section without also setting `enableDefaultDeny: {ingress: false}`.** The 1.18 CRD defaults default-deny to *true* for any direction that has rules, which silently puts the **host endpoint** into ingress default-deny and drops Talos API, Kubernetes API, kubelet, etcd, Cilium health and BGP - on 3 Talos nodes with no SSH that is a physical-console recovery. Default-deny is OR-ed across policies, so one careless new CCNP re-arms it for every host policy at once. Full mechanism, the only live host policy and its safety argument, and the audit evidence: skill `cilium-host-policy`, `kubernetes/apps/base/kube-system/cilium/app/hostpolicy-ceph.yaml`, `docs/ceph/lan-isolation-audit-results.md`.
- **A CCNP `nodeSelector` must use a label that survives into the *host endpoint's* label set, which is not the node's label set** - Cilium's default label filter strips `kubernetes.io/os` and `kubernetes.io/hostname`, so an unmatched selector **fails silently and open** (CCNP `VALID: True`, host endpoint `policy-enabled: none`). Never trust a host policy until `cilium-dbg bpf policy get <host-endpoint-id>` shows actual `Deny` rows. Measured label sets and the post-merge gate: skill `cilium-host-policy`.
- **NEVER run `tofu apply` or `tofu destroy` in `terraform/authentik/` without an explicit, current go-ahead.** It is the cluster's live SSO; a wrong apply locks every SSO-gated surface at once. A green PR, a clean plan, and a passing CI run are all necessary and none of them is the approval. `tofu plan` and state inspection are read-only and always fine. See `docs/authentik/terraform.md`.
- **Do not migrate GPU scheduling to DRA yet, and never via `adminAccess: true`.** The reference repo (`joryirving/home-ops`) schedules Intel GPUs with `resource.k8s.io/v1` claims and it looks like a clean upgrade over our `devic.es/b70` + `gpu.intel.com/xe` device plugins - it was evaluated in full on 2026-08-26 and rejected. The blocker is not our cluster (v1.36.3 serves `resource.k8s.io/v1`; `DynamicResourceAllocation` + `DRAConsumableCapacity` are enabled) and not our hardware (the driver enumerates sysfs PCI generically, so `0xe223` and `0xa7a0` are both found). It is that the only vendor driver, `intel/intel-resource-drivers-for-kubernetes`, says verbatim on `main` *"CAUTION: This is a beta / non-production software, do not use on production clusters"*, and **cannot share one GPU across pods** (upstream issue #79: *"strict 1-to-1 mapping OR SR-IOV"*) - while `vllm` and `tdarr-node` both need the single B70, so 1-to-1 strands one of them `Pending` no matter how many iGPUs the fleet has. The reference repo's claims use `adminAccess: true` + `allocationMode: All` - the only combination that lets more than one pod onto a device with this driver, but one Intel documents for *monitor* deployments, whose allocations are *"not counted by scheduler as consumed resource"*, and which needs `resource.k8s.io/admin-access: "true"` on every GPU namespace. Full design, five-stage cutover plan, alert-migration mapping, and the two upstream conditions that reopen it: `docs/ai/gpu-dra-migration-design.md`.
- **Do not merge `system-controller` or `system-upgrade` into `system`.** Evaluated in full on 2026-08-31 and rejected; both namespaces exist for a reason and neither is stateless. **k8tz**: the chart unconditionally prepends its own release namespace to the webhook's `ignoredNamespaces` (`k8tz.webhook.ignoredNamespaces` in `_helpers.tpl`), so putting k8tz in `system` *necessarily* strips TZ injection from `system` - there is no opt-out, and `webhook.ignoredNamespaces` only adds. That matters because **VolSync's cron scheduler reads the process `TZ` k8tz injects** into its manager pod (measured: `ai/hermes-r2` `10 2 * * *` -> `nextSyncTime 06:10Z` = 02:10 EDT), so losing it shifts all 90 `ReplicationSource`s by 4h/5h and collides them with kopiur's 60 `timezone`-pinned `SnapshotSchedule`s, undoing PR #1509's engine stagger. The volsync chart exposes no `env`/`extraEnv`, so the only compensation is a per-app postRenderer patch - permanently, for every future workload in `system`. The `k8tz.io/controller-namespace` label is **not** a finer-grained alternative: it excludes the whole namespace exactly like the by-name entry, and the chart defines no `objectSelector`. The move is also not atomic - `MutatingWebhookConfiguration/k8tz` is cluster-scoped and same-named across both releases, so one prune/install ordering fails every pod CREATE in all 21 covered namespaces and the other silently deletes the webhook. **tuppr**: `system-upgrade` is named in `talos/machineconfig.yaml.j2`'s `features.kubernetesTalosAPIAccess.allowedKubernetesNamespaces`, which gates its `ServiceAccount.talos.dev/tuppr-talosconfig` (`os:admin`), so a move needs `just talos apply-node` on all 3 nodes *before* the Flux change, plus recreation of a `rebootMode: powercycle` `TalosUpgrade` CR. Full evidence, the complete by-name reference list (including the `scripts/ci/` gates that hardcode these paths), and the conditions that would reopen it: `docs/system-namespace-consolidation-analysis.md`.

## UNIQUE STYLES

- **Flux variable substitution**: `postBuild.substituteFrom` references `cluster-secrets` Secret + inline `substitute` map
- **`postBuild.substitute` collision (literal `${...}` tokens)**: Flux's strict-mode envsubst runs over the *entire* built Kustomization output, so any literal `${...}` token that is not a Flux substitution variable - a Grafana dashboard variable, an app's own unresolved var - fails the **whole Kustomization**, not just the offending resource. This froze 4 apps for 44 days (#1371), and **neither `task flux:test:*` nor CI's `flate` catches it**: measured against flate v0.6.1 on this repo, an injected undefined token renders as empty and still reports `299 passed`, exit 0. Detect it live with `flux get ks -A --status-selector ready=false`. The three fixes (`kustomize.toolkit.fluxcd.io/substitute: disabled`, `$${...}` escaping, or defining the variable) with worked examples: skill `flux-substitution`.
- **Task runner split (deliberate, not migrated)**: `just` (`.justfile` + `talos/mod.just`, `bootstrap/mod.just`, `kubernetes/mod.just`) owns Talos, bootstrap, and `kube` lifecycle recipes. `task` (`Taskfile.yaml` + `.taskfiles/{domain}/`) owns the Rook operational suite and network diagnostics. Both are installed by `.mise.toml` and neither is CI-invoked. Do not port `task`'s Rook/network recipes onto `just` or vice versa - the split is intentional, not a migration in progress.
- **Component composition**: Namespace overlay `kustomization.yaml` includes common + alerts as components (`../../../components/{common,alerts}` from `apps/main/<ns>/`)
- **Volsync triple-backup**: Apps get 3 ReplicationSources (ceph/minio/r2) + 1 ReplicationDestination via a single component include on the Flux Kustomization (`../../../../../components/volsync` from `apps/main/<ns>/`). Defaults: Ceph every 4h, MinIO every 6h, R2 daily at 02:00. Per-app cron offsets live on that Kustomization's `VOLSYNC_SCHEDULE_*` (not unique across every app). Live app list and retain settings: `kubernetes/components/volsync/Readme.md`
- **One component include covers ONE volume.** Every volsync object is named from `${APP}` and Flux allows one `postBuild.substitute` map per Kustomization, so an app with a second PVC needs a second Flux Kustomization in the overlay yaml with `path: ./kubernetes/components/volsync/backup` and `APP` set to the claim name. Pattern and examples: `kubernetes/components/volsync/Readme.md` "Apps with more than one volume"
- **VOLSYNC_CACHE_CAPACITY**: Must be sized 20-50% of PVC size - small PVCs need 50-100%
- **dependsOn chains**: Many apps use `dependsOn` in the overlay Kustomization yaml - typically `onepassword-store` in `security` namespace

## NOTES

- **NEVER run `find /Users/coder`, `find $HOME`, or any unbounded search of the home directory or parent paths.** Validation agents wedge for 19-96 minutes on these searches because the home directory contains hundreds of cached clones and tool installations. When a tool or file is not found, report it and continue - do not hunt for it. The correct pattern: (1) Tools are mise-managed, resolved with `mise which <name>` / `mise exec -- <name>` and live under `~/.local/share/mise/`. (2) Cluster credentials (`kubeconfig`, `talosconfig`) do not exist in fresh worktrees and their absence is **expected and normal** - a pipeline sandbox has no cluster access. If code needs them, it should report the missing file and skip, not search for one. (3) If a tool is not mise-installed, report it explicitly rather than trying to locate it.

- **`kubernetes/clusters/main/` is the only Flux entry point.** The flux-instance HelmRelease's `values.instance.sync.path` (`kubernetes/apps/base/flux-system/flux-instance/app/helmrelease.yaml` - there is no separate `FluxInstance` CR manifest in this repo) points at `kubernetes/clusters/main`. `cluster-apps.spec.path` is `kubernetes/apps/main`; `cluster-meta.spec.path` is `kubernetes/apps/base/flux-system/meta`. Every namespace lives at `kubernetes/apps/base/<ns>/` (resources) plus overlay `kubernetes/apps/main/<ns>/` (Flux `Kustomization` CRs, one yaml per former `ks.yaml`; `default` is overlay-only scaffolding). A brand-new top-level namespace goes on `kubernetes/apps/main/kustomization.yaml` only.

- **A namespace-scoped manifest test still cannot prove a namespace is healthy - the reason changed with flate, the trap did not.** Under flux-local, `test --namespace X` never traversed into `apps/main/<ns>` at all. flate *does* always reconcile the whole tree from `--path` (there is no partial-reconcile mode), but `-n/--namespace` filters the **result and the exit code**, not just the printed lines. Measured 2026-08-29 on this repo: with a broken Kustomization in `network`, `flate test all -n monitoring` exits **0** and prints `38 passed`, while the same run unscoped exits 1. So the false green survived the migration. `task flux:test:ns` therefore runs twice - the scoped run for readable output, then an unscoped run as the authoritative gate - and `task flux:test:all` remains the plain full check; both point at the same `kubernetes/clusters/main` path as `.github/workflows/flate.yaml`. A full run is ~0.3s warm, so prefer it. Note this is a *separate* gap from the `postBuild.substitute` collision above, which a full run does not catch either.

- **`.github/workflows/validate.yaml` is the only CI signal for `talos/`, `bootstrap/`, and `.renovate/`.** Everything else (`flate`, `image-pull`) filters on `kubernetes/**` and never sees them; before it existed a `talos/`-only PR ran exactly one check, the labeler. Six path-filtered jobs on the local ARC runner: shell gates under `scripts/ci/*.sh`, plus `python-tests` which globs `scripts/ci/*-test.py` (inventory and local run notes: `scripts/ci/README.md`). Its `talosctl validate` gate is a **schema** check only: it catches render breakage and unknown machine-config keys, but **not** invalid enums, bad CIDRs, or a missing install disk - all three were tested and pass validation. Green there is not permission to `apply-node`. Per-job scope and triggers are stated in the workflow header; the `bootstrap` job covers `bootstrap/kustomize/` only, because `bootstrap/helmfile/` needs vals + 1Password to render. `terraform/` still gets validate.yaml's credential-less schema job, but live read-only plans and OCI publish live in `terraform-diff.yaml` / `terraform-publish.yaml` - see the `terraform/` NOTES entry below.
- **Retiring an app can break a `scripts/ci/*-test.py` gate that hardcodes its manifest path, and `flate` will not warn you.** Several of these tests assert `path.is_file()` on specific app HelmReleases to pin a cross-app invariant, so deleting the app makes the test fail on a missing file rather than on anything wrong with the change. Found live retiring `jellyfin` (2026-08-30): `scripts/ci/igpu-xe-allowids-test.py` holds `XE_CONSUMERS`/`B70_CONSUMERS`/`B70_VAAPI_CONSUMERS` maps of `gpu.intel.com/xe` and `devic.es/b70*` consumers by path. Before removing any app, `grep -rn '<app>' scripts/ci/` and run the affected test locally - `task flux:test:all` passes either way because the tests are not part of it.
- **A red `validate.yaml` check that passes on rerun is runner-pool contention, not a validation bug - and raising `maxRunners` is the wrong first move.** Editing the workflow file matches every per-job path filter, so the whole validate set (plus Labeler on the same scale set) can launch at once on `gha-runner-scale-set-aviator-coding-home-ops`. Measured 2026-08-29 on PR #1481: that was cluster CPU/network/disk under load, not a slot wait (`maxRunners: 15` was not the ceiling). Do not drop `.github/workflows/validate.yaml` from the per-job filters (that skips self-test of a workflow edit) and do not job-concurrency-serialize the whole set (GitHub counts concurrency wait toward `timeout-minutes`, which recreates the same cancel under queue). Measured durations, timeout floors, and the `python-tests` `needs:` ordering that keeps heavy `litellm[proxy]` pip off the lighter jobs' `mise-action` Setup Tools live in the `.github/workflows/validate.yaml` header (pinned by `scripts/ci/validate-contention-test.py`).

- `talos/*.j2` changes are not applied by Flux. `machineconfig.yaml.j2` / node overlays: render, `--dry-run`, then `just talos apply-node` per node. `schematic.yaml.j2` (kernel args + extensions) needs `just talos upgrade-node` - `apply-node` only restages the install image reference and does not boot it. Offline validation and the apply vs upgrade distinction: `talos/AGENTS.md`.
- **`talos/machineconfig.yaml.j2`'s 6 version pins (installer, kubelet, kube-apiserver/-controller-manager/-proxy/-scheduler) can drift from the live cluster.** They are a second, Renovate-managed copy of the versions that `kubernetes/apps/base/system-upgrade/tuppr/upgrades/{talosupgrade,kubernetesupgrade}.yaml` actually drive via tuppr - a Renovate PR bumping the template does **not** upgrade the cluster, and a tuppr-driven upgrade does **not** update the template. - **A VolSync restore permanently relaxes every file mode by one group-write bit, `0600` credentials included.** The mover stages its destination PVC **writable**, so kubelet's recursive `fsGroup` walk runs before restic writes: a restored volume comes back `644→664`, `755→775`, `2755→2775`, `600→660`, `444→664`. Measured across all 4,749 files of `ai/opencode` on 2026-08-31, including its `.git-credentials`. Ownership is unaffected. This is the same staging asymmetry that makes an identity mismatch invisible to VolSync and fatal to kopiur (see the kopiur trap 0 entry) - read here it means **a VolSync restore is not mode-faithful**, so do not use one to reproduce a permissions bug, and expect the relaxation to persist on the live volume afterwards. kopiur restores, which stage read-only, reproduce the original modes.
- **kopiur is live on all 30 of the fleet's 30 VolSync-protected claims and is the ONLY engine on four of them (Stage 5 pilot, 2026-09-01); three of its traps lose data or silently fail a backup.** (a) A kopiur `Snapshot` CR **owns** its kopia snapshot through a finalizer, so **deleting kopiur CRs deletes backup data** - unlike a `ReplicationSource`, which never touches the restic repository - and we run Flux with `prune: true`, which is that exact shape; **creating** a `Snapshot` deletes data too whenever it pushes an older one past GFS retention, which on every `r2` policy (no `keepHourly` tier) evicts that day's newest snapshot - `docs/backups/kopiur-wave-two-reproof-2026-09-02.md`. (b) **The mover's identity must match the workload that owns the claim's files or the backup FAILS closed**; `KOPIUR_PUID`/`KOPIUR_PGID` default to 1000 and are not cosmetic, so measure the claim's **file** ownership and never infer it from the pod's `runAsUser`. - **`envoy-internal`/`envoy-external` are Envoy Gateway (`gatewayClassName: envoy`), and a path can be blocked at that layer with a `gateway.envoyproxy.io/v1alpha1` `HTTPRouteFilter` (`spec.directResponse.statusCode`/`body`/`contentType`) referenced from an `HTTPRoute` rule via `filters: [{type: ExtensionRef, extensionRef: {group: gateway.envoyproxy.io, kind: HTTPRouteFilter, ...}}]` and no `backendRefs` - the filter answers before the request reaches any backend. Gateway API path matching is most-specific-wins regardless of rule order, so a narrower `PathPrefix` rule safely coexists with a catch-all `/` rule to the same backend on the same `HTTPRoute`. This is distinct from `agentgateway`'s own `AgentgatewayPolicy.spec.traffic.directResponse` (`kubernetes/apps/base/ai/agentgateway/app/httproute-models.yaml`), which only applies to `agentgateway.dev`-classed routes. Used to close LiteLLM's built-in `/anthropic` pass-through, which has no config-level disable: `kubernetes/apps/base/ai/litellm/app/httproute-internal.yaml`, `docs/ai-system/litellm/README.md#anthropic-pass-through-route-closed-2026-08-31`.

- **A controller that has been failing for a while does not retry the instant you fix the cause, and its status condition keeps lying until it does.** controller-runtime backs a failing reconcile off exponentially, so after a couple of dozen failures the next attempt can be many minutes out, while `status.conditions` still shows the ORIGINAL error and an ORIGINAL `lastTransitionTime`. Measured on `ai/litellm` 2026-08-27: the blocking cause was cleared and both CRs still read `Ready=False` with the stale message 18 minutes later, with zero operator log lines in that window - easy to misread as "the fix did not work" and go breaking something else. Before believing a `Ready=False`, compare its `lastTransitionTime` against `date -u` and check whether the controller has logged anything since (`kubectl -n <ns> logs deploy/<operator> --since=5m`). `kubectl -n <ns> rollout restart deploy/<operator>` clears the backoff and forces an immediate reconcile, which is the quickest way to confirm a fix. That is safe for a stateless reconciler like litellm-operator or toolhive, but think before doing it to one that is mid-operation - notably `cloudnative-pg` during a switchover or `rook-ceph` during an OSD update (see the OSD reboot rules above).
- **Removing `rpmLimit`/`tpmLimit` (or any other `*int64`/pointer field) from a `LiteLLMVirtualKey` spec stops the operator from asserting it, but does NOT clear an already-set value on the live key.** `LiteLLMVirtualKeySpec.{TPMLimit,RPMLimit}` are Go `*int64` with `json:",omitempty"` (`api/v1alpha1/litellmvirtualkey_types.go`), so a nil field marshals to nothing in the `/key/update` request body rather than an explicit JSON `null`. LiteLLM's `prepare_key_update_data` (`key_management_endpoints.py`, v1.98.0) builds the DB update via `data.model_dump(exclude_unset=True)`, which treats a field ABSENT from the request as "leave the column alone" - only a field present with value `null` clears it. Measured live 2026-08-31 on `claude-code-subscription`: removing both fields made the operator detect drift and call `POST /key/update` (`updated_at` advanced), but `rpm_limit`/`tpm_limit` stayed at their old values (`3000`/`750000000`) afterward - the update was a silent no-op for those two fields, and the operator has no way to tell (`virtualKeyRequestsEqual` will keep reporting drift and keep re-issuing the same no-op update forever). Clearing an already-set limit for real needs a one-time manual `POST /key/update {"key": "<key>", "rpm_limit": null, "tpm_limit": null}` against the proxy's admin API with the master key, confirmed by a follow-up `GET /key/info`. This only matters when an already-limited key is going unlimited; a key created with no limits from the start, or a limit that is only ever raised, never hits this gap. Same likely applies to `maxParallelRequests` (same `*int64`/`omitempty` shape) though that path is unmeasured. Full narrative: `kubernetes/apps/base/ai/litellm/app/virtualkeys/claude-code-subscription.yaml` header and `docs/ai-system/litellm/claude-code-subscription.md` §4b.

- **`terraform/authentik/` has been applied and holds live state for the cluster's SSO, and `terraform/` is not Flux-reconciled - nothing applies it automatically.** Plans run as a read-only service account and are always safe; `tofu apply` stays an explicitly approved operator action and is never a follow-on to a green PR or a clean `terraform-diff` plan comment (see ANTI-PATTERNS). Four traps `tofu validate` cannot catch are worth knowing before any edit: the S3 backend **fails open to genuine AWS** when `AWS_ENDPOINT_URL_S3` is unset; `grant_types` omitted on a *created* provider makes Authentik reject every authorize; a declared `client_secret` on an *imported* provider silently rotates it and breaks every login for that app; and `authentik_flow`'s terraform id is the slug, not the UUID. Stack inventory, what is adopted vs created vs left to Authentik's blueprint reconciler, credential minting and rotation, the state bucket, and CI: skill `authentik-terraform`, `docs/authentik/terraform.md`, `terraform/tofu.md`.

- **`healthChecks:` must target the workload, not the HelmRelease - and `wait` must stay false (or omitted; default is false).** A `HelmRelease`-kind healthCheck only reflects whether the last `helm install`/`upgrade` action succeeded - `status.conditions[Ready]` stays `True` through an ongoing pod crashloop. Verified live 2026-08-22 against `ai/hermes`: `HelmRelease.status.conditions[Ready]=True` while `Deployment.status.conditions[Available]=False`. Point `healthChecks` at the actual rendered workload (`Deployment`/`StatefulSet`/`DaemonSet`/`CronJob`, or a CR whose status is the real signal when the chart only emits the CR) to catch real failure; see `kubernetes/apps/main/ai/*.yaml` and the converted infra overlays (e.g. `cert-manager`, `flux-operator`, `intel-device-plugin-operator`) for the pattern (0 of 14 `ai` Kustomizations had any `healthChecks` before 2026-08-22, which is why `flux get ks -n ai` showed all Ready while pods crashlooped). Separately, Flux **ignores `spec.healthChecks` entirely when `spec.wait: true`** and instead assesses every object in that Kustomization's own inventory - for a helm-app overlay that is usually just the `HelmRelease`, which reopens the same crashloop blind spot. Workload `healthChecks` therefore need `wait: false` (or omitted); `timeout` still bounds the health-check evaluation. `healthCheckExprs` is not independent of that list: Flux only evaluates the CEL when `wait: true` or a non-empty `healthChecks` is set, and only against objects already in that assessment set - so a CR expression is dead code unless that CR is listed in `healthChecks` (or the whole inventory is assessed via `wait: true`). Example: `kubernetes/apps/main/system/intel-device-plugin-operator.yaml` lists `GpuDevicePlugin/xe` in `healthChecks` so its matching `healthCheckExprs` actually run.

- **A Flux `Kustomization`'s own reconcile interval will silently clobber live edits mid pre-merge test.** Editing a live `HelmRelease` directly with `kubectl` (to validate a fix before it's merged, since Flux only tracks `main`) works, but the owning Flux `Kustomization` re-applies from `main` on its own `spec.interval` (or on any `flux reconcile ks`), reverting the drift back to whatever's committed - including mid-experiment, discarding image/probe/env changes without warning. `flux suspend ks <name> -n <namespace>` before live-testing a `HelmRelease` change, `flux resume ks <name> -n <namespace>` after (this itself triggers one immediate reconcile back to `main`, which is expected and correct - the real fix only takes effect once merged). Also: raw `kubectl kustomize <app-dir>` output has no `metadata.namespace` and does not run Flux's `postBuild.substitute` - always `kubectl apply -n <namespace>` explicitly and hand-substitute (or otherwise supply) `${SECRET_DOMAIN}`-style vars, or a stray copy lands in `default`. Learned 2026-08-23 unsticking `downloads/bazarr`. **Never require live verification before merge for a brand-new app** - unlike this suspend/patch/resume flow, which live-tests a workload that already exists, a NEW app has no live workload to suspend anything for, so "confirm it's running before this is done" can only be satisfied by an out-of-band `kubectl apply` - exactly the drift GitOps prevents. For a new app, definition of done is manifests render and validate (`task flux:test:all` / `flate`); put live confirmation in a post-merge follow-up once Flux has actually reconciled it.

- **A stale `actions-runner` Talos ServiceAccount client certificate fails `image-pull` for every PR touching `kubernetes/**`, regardless of that PR's content.** The `image-pull.yaml` `pull` job's "Pull Image" step runs `talosctl --nodes $NODE image pull` using the mTLS client cert in the `actions-runner` Secret (mounted at `/var/run/secrets/talos.dev/talosconfig`), reconciled by the in-cluster `talos.dev` controller from the `ServiceAccount` CR in `kubernetes/apps/base/actions-runner-system/gha-runner-scale-set/app/rbac.yaml`. Seen live 2026-08-24: `error from node 10.10.10.12: ... remote error: tls: expired certificate`. The `remote error:` prefix means the *alert came from the peer* (the Talos node) - i.e. the node's apid rejected what talosctl presented, not a locally-detected expired server cert (that would show as a local `x509: certificate has expired` instead). That means the expired cert is the runner's own client credential, not the node's identity cert. Fix is operational, not a git commit: force the controller to reissue it, e.g. `kubectl delete secret actions-runner -n actions-runner-system` (recreated from the `ServiceAccount` CR), then re-run the workflow. The "Pull Image" step retries 4x with backoff (matching the `extract` job's pattern) to ride out transient blips, but that cannot fix an already-expired cert - every attempt hits the same rejection.

- **`linuxserver/*` images need explicit opt-in to run under this repo's hardened non-root/read-only-rootfs pod convention.** Their s6-overlay init (`docker-baseimage-alpine`) assumes it starts as root to `chown`/`usermod` before dropping privileges; under a fixed `runAsUser`/`runAsNonRoot: true`/`readOnlyRootFilesystem: true` pod, set both `LSIO_NON_ROOT_USER: "true"` and `LSIO_READ_ONLY_FS: "true"` as container env to skip those root-only init steps entirely (first-class supported, not a hack - see `init-adduser/run` in `linuxserver/docker-baseimage-alpine`). Still needed: `emptyDir` volumes at `/run` and `/tmp` (s6 writes runtime state there even read-only-rootfs-otherwise), and a `busybox` initContainer running as UID 0 to `chown` them first - `emptyDir` volumes are root-owned by default and s6-overlay's preinit refuses to start on a mismatched owner. Example: `kubernetes/apps/base/downloads/bazarr/app/helmrelease.yaml`.

- **LiteLLM has no config-file-only way to declare a virtual key with a budget or rate limit** (hence the dependency on the shared `postgres-17` CNPG cluster, and `LiteLLMVirtualKey`/`LiteLLMModel` CRs minted by the home-operations litellm-operator), **and two of its traps spend real money silently.** A fallback declared in `routerSettings` **bypasses the calling virtual key's model allow-list** - measured: a key scoped to one local model was served by `anthropic/claude-sonnet-5` and billed real USD - so a cloud fallback may only be declared on an alias whose every consumer is already cloud-entitled. And a `LiteLLMModel` with **no** `apiKey` is not credential-less: it falls back to the pod's `ANTHROPIC_API_KEY` and bills the metered account. Also never name a hand-written HTTPRoute after the `LiteLLMProxy` CR - the operator deletes it as an orphan on a *later* reconcile, so it works at first and vanishes days later. The other eight things to know before touching `ai/litellm` or `ai/litellm-operator` (accepted pod-hardening gaps, the key-alias collision that has no adopt path, D4 limits and why dragonfly is required, model-catalog routing, spend-log content storage, why per-key `aliases` grant nothing, the zero-rating gap that put ~$54 of phantom spend on the subscription key), plus the auto-router's **silent** classifier failure - a thinking model returns empty `content`, so the router fails open on 100% of traffic while looking perfectly healthy and never routing anything to a cloud tier: skill `litellm-proxy`, `kubernetes/apps/base/ai/litellm/README.md`, `docs/ai-system/litellm/`.

- **The AI reviewer that comments on pull requests is advisory-only and cannot spend money, and both properties are structural rather than configured politeness.** `.github/workflows/ai-pr-review.yaml` runs `misospace/pr-reviewer-action` on the in-cluster ARC runner against `litellm.ai.svc.cluster.local`. `publish_mode: comment` never reaches `gh pr review`, so it cannot approve, request changes, or affect branch protection; it is deliberately **not** a required check and must not become one. Its `ai-pr-review` virtual key allow-lists exactly one zero-priced, fallback-free local alias (403 on anything else, verified), and `review_routing_mode` stays `off` - which matters because it fires on every PR including this repo's heavy Renovate traffic. Fork PRs are excluded by the same guard every other in-cluster workflow carries, so they get no review at all; Renovate PRs are same-repo and ARE covered. Three traps worth knowing before touching it: it must NOT be pointed at `chat-local`, because that reasoning model returns its output in `reasoning_content` and leaves `content` - which the action parses - EMPTY (hence `models/pr-review-local.yaml`, the same `enable_thinking: false` fix the D3 classifier needs, and it only works declared on the model, never per request); its `LITELLM_PR_REVIEW_KEY` GitHub Actions secret is a hand-copied second home for the minted key, because the ARC runner has no Kubernetes API access, so **rotation has a second step that fails silently if skipped**; and its standards file is `.github/ai-review-rules.md` rather than this file, because the action hard-truncates standards to the first 16000 bytes and would deliver a mid-sentence head-slice of AGENTS.md with all of NOTES missing. Design, measured GPU/context sizing, and the verification evidence: `docs/ai-system/litellm/pr-reviewer.md`.

- **`monitoring/grafana` runs `persistence.enabled: false` (`emptyDir` SQLite), so admin-created service accounts/tokens and post-boot admin password changes are wiped on every pod restart.** `GF_SECURITY_ADMIN_USER`/`PASSWORD` (from `grafana-admin-secret`) are applied only when Grafana bootstraps a fresh DB at startup - live admin drift is cleared only by a Grafana pod restart. The token half is self-healed by `kubernetes/apps/base/monitoring/grafana-sa-provisioner` (Viewer SA/token for `ai/grafana-mcp`, pushed to 1Password `grafana-mcp`/`GRAFANA_SERVICE_ACCOUNT_TOKEN`); it cannot fix admin-credential drift itself. Details: that app's `README.md`.

- **No xpu-smi/level-zero/DCGM-equivalent GPU exporter is deployed**, so per-engine busy %, VRAM utilization and clocks are not queryable in Prometheus for either Intel GPU. What does exist - the B70's `xe` hwmon chip (temps, fan RPM, energy counters to `rate()` for live watts) and allocation-only kube-state-metrics for the iGPU, which has no hwmon chip at all: skill `intel-gpu`, `kubernetes/apps/base/ai/gpu-node-dashboard/app/gpu-node.json`.

- **Authentik's Proxy Provider + Application binding for a `SecurityPolicy`-gated route is configured out-of-band, in the Authentik UI - not GitOps.** Verified 2026-08-26 while adding `ai/opencode`: this repo has no committed Authentik blueprint/provider/application resource for any of the existing `extAuth`-gated apps (`home-assistant`, `kromgo`, `echo`) either. The Kubernetes side of the pattern (a `SecurityPolicy` with `extAuth` pointed at `ak-outpost-authentik-embedded-outpost` in `security`, targeting the app's `HTTPRoute`) is fully GitOps-owned and green in `flate`, but the outpost will not actually authorize a *new* hostname until the captain creates the matching Proxy Provider + Application in Authentik itself - treat that as a captain prerequisite for any new gated route, the same class of gap as a missing 1Password item.

- **A recyclarr `assign_scores_to` entry must match by `trash_id`, never by profile `name`.** A TRaSH guide rename silently orphans every name-matched custom-format score onto whatever profile still holds the old name, while recyclarr creates a new profile under the new name that gets none of the intended scoring - happened here 2026-04-09 to 2026-08-29, when a rewrite renamed `SQP-1 (2160p)` to `[SQP] SQP-1 (2160p)` and every subsequent custom-format change (including a real fix, PR #1369) landed on a 2-movie orphan instead of the 240-movie profile in use. `trash_id` matching is immune to the rename. Root cause, the compounding `min_format_score` override, and the fix: `docs/media-stack.md#recyclarr---declarative-quality-config`. Which movie sits on which Radarr quality profile is Radarr database state, not GitOps - recyclarr only creates/scores profiles, it never assigns a movie to one - so a profile restructure (as in the 2026-08-29 fix) needs a one-off Radarr API pass, documented in the same section.

- **Radarr never searches for a monitored-but-missing movie on its own** - there is no scheduled missing-movie task and every import list runs `searchOnAdd: false`, so a movie a list adds just sits with no file until a matching new RSS release happens to appear or a human triggers a search. This is why the SQP-1 profile fix above needed a separate, deliberate 347-movie backlog search rather than just fixing the config and waiting. That search must be sized against free disk **before** running - a few hundred movies at even moderate quality can be multiple TB, and nothing else in the stack checks that first. Procedure, sizing method, and staged/rate-limit-safe search pattern: `docs/media-stack.md#backlog-missing-movie-search`.

- **An app can be denied write access to its own PVC while every signal in the cluster stays green, and NOTHING in CI catches it.** Two of six audited volumes were empty for this reason (2026-08-30). The mechanism is always the same: a volume root ends up owned `*:1000` - the stamp of a VolSync restore mover, whose `VOLSYNC_PUID`/`PGID` both default to `1000` (`kubernetes/components/volsync/*/replication*.yaml`) - and the pod then declares no matching `fsGroup`, so the kubelet does no ownership fix-up and the process falls through to the `other` bits of a `2775` directory. The app is `Ready`, its probes pass, Gatus is green, and VolSync cheerfully backs the empty volume up three times a day. Two shapes seen: `downloads/autobrr` declared `runAsUser/Group: 2000` and simply never had an `fsGroup` (it logged `open /config/config.toml: permission denied` at every start for ~11 months); `selfhosted/rsshub-playwright` had a correct securityContext under the key `selfhostedPodOptions`, which the app-template chart does not know, so Helm silently discarded it and the pod shipped `securityContext: {}`. **`flate` does not flag either** - measured directly by reinstating the typo, which leaves the run at `308 passed` with the same 4 pre-existing warnings. Its `values not used by the chart` warning fires from a chart's own values schema (coder, dragonfly-operator, surrealdb, cilium) and app-template's is too permissive to catch a bogus top-level key. So a wrong pod-options key is invisible to every gate this repo has. The cheap generic detector, still unbuilt: for every PVC-mounting workload, exec `test -w <mountPath>` and alert on failure. Fix pattern and the fsGroup mechanics: `kubernetes/apps/base/downloads/autobrr/app/helmrelease.yaml`.
- **`fsGroup` does re-own existing content on this cluster, and `OnRootMismatch` does not prevent that.** Both Ceph CSI drivers are `fsGroupPolicy: File` (`kubectl get csidriver`), so the kubelet applies `fsGroup` to `ceph-block`/`ceph-filesystem` claims. `fsGroupChangePolicy: OnRootMismatch` skips the recursive walk only when the volume root ALREADY matches, so changing a declared `fsGroup` (or adding a first one) is exactly the mismatch that triggers the full recursive chown on the next mount - measured on autobrr, whose root went `root:1000` -> `root:2000` and which then wrote its `config.toml` immediately. One consequence worth knowing before a rollback: that chown **persists on the volume** after the manifest is reverted, so an app whose gid now matches the volume group keeps working without the `fsGroup` line, and a later `git revert` will not reproduce the original failure.
- **Helm cannot un-set a field it never set, so a `kubectl patch` of a pod `securityContext` survives `flux reconcile --force`.** Live-testing a HelmRelease change via the sanctioned suspend -> patch -> resume flow leaves real drift behind: Helm's 3-way merge removes only keys present in its own previous release manifest, so fields added by hand (`fsGroup`, or a whole `securityContext` the chart never rendered) stay on the Deployment indefinitely while `flux get ks` reports Ready and `Applied revision: main`. Verified 2026-08-30 - the `volumes` list reverted correctly on reconcile because the chart owns it, and the hand-added `securityContext` keys did not. Undo them explicitly with a merge patch setting each key to `null` and then confirm the live object matches git; do not assume `resume` plus a forced reconcile restored the cluster.

## Maintaining this file

`CLAUDE.md` is a symlink to this file - there is only one copy to maintain, and edits here are
automatically visible under either name. Do not recreate `CLAUDE.md` as a separate file.

Keep this file for knowledge useful to almost every future agent session in this project.
Do not repeat what the codebase already shows; point to the authoritative file or command instead.
Prefer rewriting or pruning existing entries over appending new ones.
When updating this file, preserve this bar for all agents and keep entries concise.

### Where a new finding goes

> A finding lands in its own document or a subsystem skill. It earns an `AGENTS.md` line only when
> it fits in one sentence plus a pointer AND an agent who has not yet decided to touch that
> subsystem needs it.

This file is loaded into every session in this repo before any work starts, so every line here is
paid for by every agent, including the ones that never go near the subsystem it describes. It grew
about fifteen-fold in eleven days entirely as depth *inside* existing bullets, which is why the
rule is about depth rather than entry count.

The other cost is duplication: roughly 95% of this file is original re-phrasing rather than
quotation, so each summary here is a second copy that has to be maintained independently of the
document it summarises, and it drifts. That already happened - this file and
`docs/backups/kopiur-stage5-pilot-retirement-2026-09-01.md` both carried the kopiur restore
prerequisite as "raise the cache AND prove an r2 restore" after `media/plex`'s raise to 10Gi had
already landed, while the source proof document recorded the standing values correctly.

So: write the finding once, where it is owned. Add a subsystem skill under `.claude/skills/` when
the audience is "an agent working on that subsystem" - the `description` line is the load trigger,
so state the trigger condition precisely; a vague one means the skill never loads when it is
needed. Keep an always-loaded line here only for a tripwire: silent data loss, a cluster-wide
outage, or an unrecoverable state, where an agent needs the warning *before* deciding to touch the
subsystem at all.
